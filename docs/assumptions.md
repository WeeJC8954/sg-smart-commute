# Assumptions

Documented values to review once working test journeys exist. See guide v2.1 §0.1.

| Area | Assumption | Value | Source / note |
|---|---|---|---|
| SG bounds | Valid GPS/geocode coordinates | lat 1.15–1.48, lng 103.60–104.10 | Bounding box. It includes some sea and Johor Strait. That is accepted |
| Location timeout | Acquisition timeout, started after permission is granted | 10 s | Guide §5.1 |
| Walking estimate | `ceil(haversine × 1.3 / 80)` minutes. 0 m gives 0 min | detour 1.3, 80 m/min | Labelled "~N min walk (est.)" everywhere. Ignores barriers, bridges, expressways, rivers. Values in `JourneyConfig` |
| Bus candidates | Stops within the radius of origin and of destination (haversine). If the first radius gives **no direct match** (no candidates on a side, *or* candidates but no connecting service), retry **once** at the widened radius on both sides | 400 m → 800 m | Guide §9.2; the M3 brief's "if no useful candidates exist". Configurable (`PlannerConfig`) |
| Bus scoring | `score = walkToStop_min + walkFromStop_min + 1.5 × stops` (lower is better). Best option per service by (score, stops, direction, board code, alight code). Overall top 3 by (score, stops, service number in natural order: `2` < `9A` < `10` < `CT18`) | weights as shown | A heuristic, never called "best"/"optimal". Review once working journeys exist (guide §0.1 item 5) |
| Route segments | Per service direction, each origin-candidate occurrence `i` pairs with the **first** occurrence `j > i` of each destination candidate. The shortest such segment over all occurrences is kept (covers loops and repeated stops). Never `d` before `o`; never `o == d`. Direction is never inferred from geography: only the ordered lists. "Toward" = the last stop name of that direction's list; loops (first == last stop) say "(loop service)" | — | Guide §9.4; M3 brief. Real cases tested: loop 4, one-direction 184, 265 (54009 at 13 and 28), 647 (43589 at 22 and 23) |
| Opposite-side stops on a loop | When both an outbound stop and its opposite-side return-leg stop are within the radius (e.g. 76231 / 76239 on loop 4, 29 m apart), the planner may board on the return leg if that is fewer stops. This follows the rules; it is not a special case | — | Found on real data in M3 |
| Journey scope | Direct bus only, zero transfers. No live arrival times in M3 ("Live bus arrival times are not available yet.") | — | MRT is information only: station name and est. walk |
| Walk instead | Suggest walking (and skip loading bus data) when origin and destination are close | ≤ 300 m straight line | Guide §9.2 step 9 |
| Transport data bounds | busrouter stops and MRT exits are range-checked against lat 1.10–1.60, lng 103.50–104.20, not the GPS `SgBounds`: 46239 Larkin Ter (JB) is valid data. Distance filtering keeps it out of Singapore journeys | — | M3 review. Also catches a lat/lng swap |
| busrouter validation | Malformed entries are dropped and counted. The dataset fails (`StaticDataUnavailable`) if the top level is wrong, nothing is valid, or > 5 % of stops or services are invalid. Unknown stop codes are removed from a route; a route with < 2 stops is dropped | 5 % | Tolerates a stray record; treats a schema change as failure |
| Bus data caching | Loaded on the first journey that needs it (not at launch, not for walk-only), held for the session by `busNetworkProvider` and the repository. Concurrent callers share one download. A failure is not cached; Retry reloads | session | Guide §9.1, §15. HTTP timeout 10 s |
| MRT stations | Exits grouped by `STATION_NA`. Seven code-only names (CC9, DT18, DT4, NE18, CC30, CC31, CC32) are renamed **only** through a cited table (OneMap returns exactly that code label 41–85 m from the exits). An unverified code-only name stays a separate code-labelled station, never merged by proximity. The nearest station is measured to its **nearest exit**. Stations beyond 1.5 km are not suggested ("none within about 1.5 km") | 1.5 km | M3 review. No line/code table is bundled, so none is shown |
| Staleness | Forecast / PM2.5 / PSI / UV stale thresholds | 3 h / 2 h / 2 h / 2 h (daytime) | Starting values, not official cadences |
| Bus arrival | Manual refresh; cache | ≤ 20 s | Auto-polling deferred |
| Caching | Session-only, in memory | — | Offline cold start → *Network unavailable* + Retry |
| data.gov.sg | Anonymous rate limit | 6 calls / 10 s | Official guide, 2026-10-01 |
| Place search | Strip `Blk`/`Block`, trim, collapse whitespace before querying. Only a leading `Blk`/`Block`/`Blk.` followed by a block number **and** a street is stripped (`Blk 123 Ang Mo Kio Ave 6` → `123 Ang Mo Kio Ave 6`). `Block 71` or `Blk 123` alone are kept as typed | — | Milestone 0 eval: `Blk 123 …` failed on OneMap/Nominatim. Re-confirmed on 2026-10-01: OneMap returns 0 results for the raw `Blk` form (fixture `hdb-blk-raw.json`), and the app finds 2 for the same input |
| Place search | 6-digit postal-code queries accept only an exact postcode match | — | Photon is fuzzy (`640512` → `640517`) |
| Time | Display at a fixed +08:00 offset; negative ages shown as "just now" | — | Singapore has no DST |
| Manual origin (M2) | The M1 NEA-area picker is **replaced** by OneMap place search (§5.3). The user types a postal code, street, building, mall or landmark and taps one result. The origin is that place's coordinates, with provenance `manual` and its address as detail. The same `PlaceSearchField` is used for the destination | — | Guide §5.3, §5.5. M2 scope |
| OneMap "error" field | Every tokenless response carries `"error": "Authentication token missing…"`, **including genuine no-result queries** (`000000`, raw `Blk 123 …`). So `error` + an empty `results` list means *no results*, not token enforcement. Enforcement is detected as HTTP 401/403, or a body with an `error` and **no** `results` list at all. Both map to `ApiUnauthorized` ("OneMap now requires sign-in"). No credential, proxy or workaround is added | — | Differs from the guide's §8.2 wording ("error with empty results" → failure), based on the fixtures captured 2026-10-01. Revisit if OneMap's behaviour changes |
| Reverse geocoding | Not used. Tokenless `GET /api/public/revgeocode` answered **401 Unauthorized** (probed 2026-10-01 14:48 UTC). `reverseGeocode` returns null without a request, and a GPS origin stays labelled "Current location" | — | M2 instruction: no workaround if it needs authentication |
| Place type | OneMap does not label result types. Only `mrtStation` (name contains "MRT STATION" / "LRT STATION"), `building` (a `BUILDING` value) and `address` (a block or street without a building) are inferred. Malls and POIs are not distinguished from other buildings | — | Avoids guessing |
| Place search UX | Debounce 350 ms; submit (Enter) searches at once. Minimum 3 characters unless a 6-digit postal code. A sequence token drops obsolete responses. Successful results are cached in memory per normalised query for 5 min; failures are not cached. Only page 1 of OneMap results (≤ 10) is shown. Nothing is selected without a tap, even a single exact postal match. A subtitle identical to the name (HDB blocks) shows the postcode instead. The three values are defined once, in `PlaceSearchConfig` (`lib/core/config/app_config.dart`) | 350 ms / 3 chars / 5 min | Guide §8.3, §15 |
| Late fix | A valid late fix populates the origin only if the user has neither selected a place nor started typing (focus or input in the origin search field). Otherwise it is offered as a "Use my current location" chip. Out-of-SG late fixes and late errors are ignored. A fix (in time or late) from any attempt, including one started by "Try location again", never replaces a manual origin: it is only offered. Only tapping "Use my current location" switches a manual origin back to GPS. With a manual origin set, "Try location again" runs in the background, and its denial, timeout, error or out-of-SG result changes nothing. Each attempt has an id: a superseded attempt's fix, error or timeout is dropped and never counts as the current attempt's result | — | Guide §5.4. Reviewer rule on PR #3 |
| Location errors | Any acquisition error not covered by §13 maps to `LocationUnavailable` (added to the §13 list) | — | e.g. a geolocator `PositionUpdateException` |
| Web location | Browsers report the service as always enabled; a blocked browser permission surfaces as "denied". No "Open settings" action on Web | — | geolocator_web behaviour |
| UV at night | Night = before 07:00 or from 20:00 SGT. At night the last reading is shown with its time under "UV not measured at night" and is never marked stale | 07:00–20:00 | Readings observed 07:00–19:00 on 2026-10-01 |
| Forecast staleness | Measured from the payload `update_timestamp` | 3 h | Guide §6.3 |
| PM2.5 / PSI staleness | Measured from the reading `timestamp` (the hour) | 2 h | Guide §6.3 |
| Dashboard refresh | Manual refresh-all (4 calls) is ignored for 15 s after the previous one (a UX debounce only). Retry is per dataset (1 call). Riverpod 3's automatic provider retry is disabled. There is no automatic polling | 15 s | UX |
| data.gov.sg client-side limit | One rolling-window limiter for every v2 real-time send: at most 6 in any 11 s window (the 10 s limit plus a 1 s margin, because the server counts arrival times and latency varies). Calls beyond it wait in FIFO order; nothing is dropped. The launch burst of 4 is not delayed. The limiter uses the device clock: a backwards clock jump only delays calls, and a forward jump could at worst draw a real 429, which is still handled | 6 per 10 s + 1 s | data.gov.sg anonymous limit; PR #3 review |
| Band tables | 24-hr PSI: Good 0–50, Moderate 51–100, Unhealthy 101–200, Very unhealthy 201–300, Hazardous > 300. 1-hr PM2.5 (µg/m³): Normal 0–55, Elevated 56–150, High 151–250, Very high ≥ 251. UV: Low 0–2, Moderate 3–5, High 6–7, Very high 8–10, Extreme ≥ 11 | — | Sources in `data-sources.md` (checked 2026-10-01) |
