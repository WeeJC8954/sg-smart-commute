# Assumptions

Documented values to review once working test journeys exist. See guide v2.1 §0.1.

| Area | Assumption | Value | Source / note |
|---|---|---|---|
| SG bounds | Valid GPS/geocode coordinates | lat 1.15–1.48, lng 103.60–104.10 | Bounding box. It includes some sea and Johor Strait. That is accepted |
| Location timeout | Acquisition timeout, started after permission is granted | 10 s | Guide §5.1 |
| Permission timeout | **Amends the row above (issue #9).** The permission step has its own bound: if the prompt is not answered within it, the manual origin prompt is shown with "The location request has not been answered yet." The attempt is not abandoned. If the prompt is granted later and the user has neither typed nor chosen a place, acquisition starts then (with its own 10 s timeout); otherwise the fix follows *Late fix* (only offered) and the "not answered" note is removed, since it is no longer true (M5, seen live in Chrome). A later denial replaces the reason. Needed because on Web `Geolocator.requestPermission()` is a `getCurrentPosition()` call with no timeout, which stays pending while Chrome's prompt is open | 10 s (`AppTimings.locationPermissionTimeout`) | Chrome smoke item 1 (M4) |
| Walking estimate | `ceil(haversine × 1.3 / 80)` minutes. 0 m gives 0 min | detour 1.3, 80 m/min | Labelled "~N min walk (est.)" everywhere. Ignores barriers, bridges, expressways, rivers. Values in `JourneyConfig`. **Known Phase 1 limitation:** a straight line × 1.3 cannot tell whether reaching a stop means crossing a road, or whether that crossing needs a pedestrian crossing, an overhead bridge, an underpass or a longer route. Real walking routing could improve this in Phase 2 |
| Bus candidates | Stops within the radius of origin and of destination (haversine). If the first radius gives **no direct match** (no candidates on a side, *or* candidates but no connecting service), retry **once** at the widened radius on both sides | 400 m → 800 m | Guide §9.2; the M3 brief's "if no useful candidates exist". Configurable (`PlannerConfig`) |
| Bus scoring | `score = walkToStop_min + walkFromStop_min + 1.5 × stops` (lower is better). Best option per service by (score, stops, direction, board code, alight code). Overall top 3 by (score, stops, service number in natural order: `2` < `9A` < `10` < `CT18`) | weights as shown | A heuristic, never called "best"/"optimal". Review once working journeys exist (guide §0.1 item 5) |
| Route segments | Per service direction, each origin-candidate occurrence `i` pairs with the **first** occurrence `j > i` of each destination candidate. The shortest such segment over all occurrences is kept (covers loops and repeated stops). Never `d` before `o`; never `o == d`. Direction is never inferred from geography: only the ordered lists. "Toward" = the last stop name of that direction's list; loops (first == last stop) say "(loop service)" | — | Guide §9.4; M3 brief. Real cases tested: loop 4, one-direction 184, 265 (54009 at 13 and 28), 647 (43589 at 22 and 23) |
| Opposite-side stops on a loop | When both an outbound stop and its opposite-side return-leg stop are within the radius (e.g. 76231 / 76239 on loop 4, 29 m apart), the planner may board on the return leg if that is fewer stops. This follows the ordered-route / shortest-valid-segment rules; it is not a special case. **No "same side of the road" rule is added:** busrouter has no side-of-road field, and any geometric rule would be arbitrary. The walk to the opposite-side stop is the haversine estimate, so it does not include crossing the road (see *Walking estimate*). Known Phase 1 limitation | — | Found on real data in M3. Regression test on the real fixture: `test/features/journey/busrouter_test.dart`, "loop 4: an opposite-side stop on the return leg…" (boards 76239, 5 stops) |
| Journey scope | Direct bus only, zero transfers. Live arrivals (M4) are added to the displayed options; they never change the plan | — | MRT is information only: station name and est. walk |
| Walk instead | Suggest walking (and skip loading bus data) when origin and destination are close | ≤ 300 m straight line | Guide §9.2 step 9 |
| Transport data bounds | busrouter stops and MRT exits are range-checked against lat 1.10–1.60, lng 103.50–104.20, not the GPS `SgBounds`: 46239 Larkin Ter (JB) is valid data. Distance filtering keeps it out of Singapore journeys | — | M3 review. Also catches a lat/lng swap |
| busrouter validation | Malformed entries are dropped and counted. The dataset fails (`StaticDataUnavailable`) if the top level is wrong, nothing is valid, or > 5 % of stops or services are invalid. Unknown stop codes are removed from a route; a route with < 2 stops is dropped | 5 % (`BusrouterValidation.maxInvalidShare`) | Tolerates a stray record; treats a schema change as failure |
| Bus data caching | Loaded on the first journey that needs it (not at launch, not for walk-only), held for the session by `busNetworkProvider` and the repository. Concurrent callers share one download. The repository does not cache a failure, but `busNetworkProvider` holds the error until the user taps Retry (which reloads); changing origin/destination does not reload it | session | Guide §9.1, §15. HTTP timeout 10 s |
| MRT stations | Exits grouped by `STATION_NA`. Seven code-only names (CC9, DT18, DT4, NE18, CC30, CC31, CC32) are renamed **only** through a cited table (OneMap returns exactly that code label 41–85 m from the exits). An unverified code-only name stays a separate code-labelled station, never merged by proximity. The nearest station is measured to its **nearest exit**. Stations beyond 1.5 km are not suggested ("none within about 1.5 km"; the distance in that text is generated from the same value the lookup uses) | 1.5 km (`JourneyConfig.mrtMaxDistanceMeters`, via `mrtMaxDistanceMetersProvider`) | M3 review. No line/code table is bundled, so none is shown |
| Staleness | Forecast / PM2.5 / PSI / UV stale thresholds | 3 h / 2 h / 2 h / 2 h (daytime) | Starting values, not official cadences |
| Bus arrival cache | One ArriveLah request per distinct boarding stop of the displayed options, reused for the TTL, counted from when the answer arrived. Concurrent requests for a stop share one call. Failures are not cached | 15 s (`BusArrivalConfig.cacheTtl`) | Guide §10/§15 says ≤ 20 s; ArriveLah sends `max-age=15`, so asking sooner only returns the same cached answer |
| Bus arrival refresh | Manual "Refresh arrivals" button only. It re-reads arrivals (no request for a stop inside the TTL) and records a new check time. It never recomputes or reloads the static route. No automatic polling | — | Guide §10: polling optional and deferred |
| ETA format | ETA = estimated arrival − now (the clock, re-read on every UI tick, so ETAs count down between checks). At most 1 min away, or already past → `Arr`; otherwise whole minutes **rounded down** (`61 s` → `1 min`, `7 min 59 s` → `7 min`). Up to 3 per option, soonest first. A schedule-based estimate (`monitored` 0) is marked `(scheduled)` | 1 min (`arrivingWithin`), 3 (`maxShown`) | Rounding down never tells a rider they have more time than estimated. Screen readers hear "arriving now" / "N minutes" |
| ETA bounds | ArriveLah is an unofficial proxy, so a well-formed time is still checked against now: more than 2 min in the past (the bus has left, or a replayed old body) or more than 3 h ahead (LTA lists the next three buses, never hours ahead) counts as no time. It is dropped before sorting, so it never shows as `Arr` and never pushes a real bus out of the three shown | 2 min / 3 h (`BusArrivalConfig.maxPastEta` / `maxFutureEta`) | Issue #15. Up to 2 min past is still `Arr`: the bus may be at the stop |
| Outdated arrivals | Once the last check is more than 3 min old, each option shows "Times checked over 3 min ago. Refresh arrivals for current times." instead of minutes. Nothing is requested until the user taps Refresh | 3 min (`BusArrivalConfig.outdatedAfter`) | Issue #11. Estimates drift as buses are delayed; a countdown from an old check would look current |
| UI tick | Time-relative text ("N min ago", the Out-of-date marker, the UV night rule, bus ETAs) is recomputed every 15 s while the screen is open (`uiTickProvider`). It is a rebuild only, never a request, so the "no automatic polling" rule still holds | 15 s (`AppTimings.uiTick`) | Issue #11 |
| Missing arrival | A service not listed at its stop, or listed with no valid (or no plausible, see *ETA bounds*) time in any slot → "No live arrival available". It is not evidence that the route is invalid (e.g. 651 is a peak-hour City Direct service, absent off-peak). Never "0 min" | — | M4 |
| Source timestamp parsing | Every provider timestamp (NEA and ArriveLah) goes through one strict helper, `parseSourceTimestamp` (`core/time/sgt_format.dart`): ISO-8601 `YYYY-MM-DDTHH:MM[:SS[.fff]]` with an explicit offset (`Z`, `±HH:MM` or `±HHMM`; offset < 24 h, minutes < 60), and the parsed instant must give back exactly the fields that were sent. `DateTime.parse` alone rolls `2026-13-45T25:00` over into a different instant and reads a value without an offset as device-local time. A rejected value is "no estimate" for an ArriveLah slot and `InvalidApiResponse` for an NEA dataset (as for any other malformed field) | — | Found by an M4 unit test (ArriveLah), then applied to NEA in the PR #8 follow-up |
| Loop terminal arrivals | When the rider boards a loop at the stop where it starts and ends, arrivals with LTA `visit_number` 2 are buses finishing the loop and are excluded. Visit-1 arrivals are kept, and so are arrivals whose `visit_number` is missing or unknown (not discarded on missing metadata). If this leaves no timed arrival for the service, the option shows "No live arrival available". Elsewhere all timed entries are shown | — | Observed at 75009 Tampines Int: loop 291 lists visit 2 (GPS-tracked, arriving) and visit 1 (scheduled departures on the minute). A stop visited twice mid-loop is not disambiguated (known limitation) |
| Arrival optional fields | `load`, `feature`, `type`, `monitored`, `visit_number`: an unknown or missing value becomes "not shown" and never makes a valid ETA unusable. Only the next bus's details are shown, in words (never colour alone); "Wheelchair accessible" is shown only when marked | — | M4 |
| Arrival failure | Per stop: one stop failing does not hide another stop's arrivals. The route, walks and MRT stay visible; the option shows "Live arrivals: <reason>" + Retry | — | M4 |
| Stale arrival answers | Arrivals are tagged with the exact plan they were fetched for and shown only against that plan, so an answer for an earlier journey is never shown on a newer one, even for the same stop | — | Same discipline as M2 place search |
| Caching | Session-only, in memory | — | Offline cold start → *Network unavailable* + Retry |
| Response size cap | Every provider response goes through `JsonHttpClient`. A 2xx body larger than the cap is rejected as *InvalidApiResponse* (not retried): a declared `Content-Length` over the cap is refused without reading the body, otherwise reading stops as soon as the cap is passed. Non-2xx bodies are not read (status and headers only). On Web the browser has already downloaded the body by then, so the cap there bounds decoding and memory held by the app, not the transfer | 4 MiB (`AppTimings.httpMaxResponseBytes`) | M5. Largest real payload measured 2026-10-02: busrouter `stops.min.json` 317,155 bytes (services 255,411; data.gov.sg, OneMap, ArriveLah ≤ 8 KB), so > 12× headroom |
| Retry-After | After a 429 with a `Retry-After` in seconds, `JsonHttpClient` sends nothing more to that host until it has passed: each request (Retry, Refresh all, a new search) fails at once with *ApiRateLimited* carrying the time left, and the message says how long ("Please retry in 4 seconds."). The wait is capped, so a bad header cannot lock a provider out for the session; the cap is applied to the number before it becomes a duration, so a huge value cannot overflow. Only RFC 9110 delay-seconds (digits) count: a missing, empty, signed, fractional, zero or HTTP-date value means no hold (the generic "retry in a moment"). The hold is checked before a rate-limiter grant (a held request takes none) and again after it, so a request queued in the limiter when the 429 arrives is not sent either; a request already on the network keeps its answer. Of two concurrent 429s, the later end wins. The hold is per host: all data.gov.sg datasets share one host (and one quota), so a 429 on one holds the four; other hosts are unaffected. A busrouter 429 still surfaces as *Bus data is unavailable* (static data failures are not split by cause) | at most 60 s (`AppTimings.maxRetryAfter`) | Issue #30 |
| Failure detail | Every failure's technical `detail` (parser field, HTTP status, wrapped exception) is kept on the `AppFailure`, shown in its `toString`, and logged with `debugPrint` in debug builds only, at the one boundary where a load becomes a user-facing state (`guardAppFailure`: the Conditions, bus network, MRT, arrivals and place search loads). It is never shown to the user. Release builds log nothing | — | Guide §13; issue #31 |
| Arrivals footer layout | The ArriveLah attribution and "Refresh arrivals" sit side by side while the footer has at least 280 dp × the text scale; otherwise the button goes below the attribution and its label may wrap. M5: on a 360 dp phone at Android font scale 2.0 the side-by-side footer broke words mid-way ("Arrive / Lah", "check / ed"); widget tests at 2× (FlutterTest font) reported a RenderFlex overflow of 176 px (360 dp) / 216 px (320 dp) | 280 dp (`HomeLayout.arrivalsFooterMinRowWidth`) | Same text-scale rule as the Conditions grid breakpoints |
| Motion | The route and journey cards animate their height when their content changes, from the top edge, decelerating with no overshoot (`Curves.easeOutCubic`); a change mid-animation continues from the current size. The system reduce-motion setting makes changes instant. One `MotionSize` per card, never nested. At zero duration (reduce motion, or tests via `buildTestApp(motionDuration:)`, default zero) no `AnimatedSize` is used at all, because `AnimatedSize` asserts with a zero duration; a `GlobalKey` keeps the card's content (e.g. typed text) when the setting changes while the app runs | 250 ms (`AppMotion.resize`) | UI polish. Apple design guidance: a critically damped spring with a 0.3–0.4 s response |
| Theme | Light and dark themes from one teal seed; the app follows the system setting. Colours come only from the scheme | — | UI polish |
| Origin line | "From: <label>" for both provenances (GPS: "From: Current location"); the icon shows GPS vs a searched place. Provenance stays in the domain (§5.4). Origin and destination share one route card | — | UI polish; matches §16 "From: Current location" |
| Reading tiles | The metric label ("24-hr PSI", "1-hr PM2.5", "UV index") is the tile title, shown once; the value is large; the band is a text pill in one neutral colour for every band (no colour scale). Each tile keeps its own scope and timestamp (§7). A reading past its threshold says "Out of date". The refresh button sits beside the Conditions heading | — | UI polish |
| Journey options | Each option leads with its service badge, "Take Bus N toward X" and the live times, then the steps in rider order (walk, N stops, alight, walk). An alternative shows only its first step, the walk to its boarding stop (so its live times always name their stop, which may differ from the suggestion's); "Show steps" reveals the rest (spoken as "Show steps for Bus N", since each alternative has one). The suggestion is always open. No total journey time is shown: there is no in-vehicle time, so a total would be invented | — | UI polish |
| Screen readers and focus | Section titles (Conditions, the origin and destination prompts, Suggested journey, Alternatives, MRT alternative) are headings. Buttons that repeat on screen carry a spoken label that names their target: "Change origin" / "Change destination", "Retry 24-hr PSI", "Retry place search", "Retry live arrivals for Bus N", "Retry finding a bus", "Retry finding the nearest MRT" (the visible text stays "Change" / "Retry"). Place-search status lines (too short, no results, N matches, searching, a failure) are live regions, so they are announced when they appear; the results list is not. Focus: "Change" opens a focused search field; picking a place, or "Keep this …", puts focus on that card's "Change". A search field shown unasked (the launch fallback, the first destination prompt) is not focused, so no keyboard pops up unasked | — | Guide §16 accessibility; issues #25–#27, #29 |
| Place search clear | A clear (×) button empties the field and its results and selects nothing. Choosing a result gives one selection haptic (a no-op on Web) | — | UI polish |
| data.gov.sg | Anonymous rate limit | 6 calls / 10 s | Official guide, 2026-10-01 |

| Manual origin (M2) | The M1 NEA-area picker is **replaced** by OneMap place search (§5.3). The user types a postal code, street, building, mall or landmark and taps one result. The origin is that place's coordinates, with provenance `manual` and its address as detail. The same `PlaceSearchField` is used for the destination | — | Guide §5.3, §5.5. M2 scope |
| OneMap "error" field | Every tokenless response carries `"error": "Authentication token missing…"`, **including genuine no-result queries** (`000000`, raw `Blk 123 …`). So `error` + an empty `results` list means *no results*, not token enforcement. Enforcement is detected as HTTP 401/403, or a body with an `error` and **no** `results` list at all. Both map to `ApiUnauthorized` ("OneMap now requires sign-in"). No credential, proxy or workaround is added | — | Differs from the guide's §8.2 wording ("error with empty results" → failure), based on the fixtures captured 2026-10-01. Revisit if OneMap's behaviour changes |
| Reverse geocoding | Not used. Tokenless `GET /api/public/revgeocode` answered **401 Unauthorized** (probed 2026-10-01 14:48 UTC). `reverseGeocode` returns null without a request, and a GPS origin stays labelled "Current location" | — | M2 instruction: no workaround if it needs authentication |
| Place type | OneMap does not label result types. Only `mrtStation` (name contains "MRT STATION" / "LRT STATION"), `building` (a `BUILDING` value) and `address` (a block or street without a building) are inferred. Malls and POIs are not distinguished from other buildings | — | Avoids guessing |
| Place search UX | Debounce 350 ms; submit (Enter) searches at once. Minimum 3 characters unless a 6-digit postal code. A sequence token drops obsolete responses. Successful results are cached in memory per normalised query for 5 min, for at most 50 queries (least recently used evicted first; expired entries dropped on every write); failures are not cached. The field takes at most 100 characters, and a longer query (e.g. pasted) is cut to 100 before it is sent. Only page 1 of OneMap results (≤ 10) is shown. Nothing is selected without a tap, even a single exact postal match. A subtitle identical to the name (HDB blocks) shows the postcode instead. The origin and destination cards never repeat such an address under the name (`Place.distinctAddress`). The values are defined once, in `PlaceSearchConfig` (`lib/core/config/app_config.dart`) | 350 ms / 3 chars / 5 min / 100 chars / 50 queries | Guide §8.3, §15 |
| OneMap rate limit | **OneMap publishes no number, and none is claimed.** Since issue #16 the client paces itself conservatively: every OneMap send (type-ahead, submit, Retry and each automatic retry, from both search fields) goes through one shared rolling-window limiter allowing 1 request per 1 s; further sends wait in FIFO order, nothing is dropped. This is a pace chosen below the observed 429, not OneMap's limit. Known trade-off: a superseded type-ahead query still uses its turn (its answer is then ignored), so the newest query can wait about 1 s per queued one. Observed only: HTTP 429 after 2–3 search calls within about 1.5 s (curl, 2026-10-01 and 2026-10-02). The 429 is `text/html` with **no `Retry-After`, no rate-limit headers and no `Access-Control-Allow-Origin`**. OneMap's search docs list "429 - API limit exceeded" with no number, and the API terms of service state none. The rest of the handling is kept: 350 ms debounce, 5-min result cache, in-flight dedup, 429 → `ApiRateLimited` (with `retryAfter` null, since there is no header). On Web the browser hides that 429 (no CORS header), so the client sees a network error → `NetworkUnavailable`, after its bounded retries | 1 per 1 s (`OneMapRateLimit`) | Risk, see `data-sources.md` § OneMap and the 2026-10-02 run-log rows in `testing.md` |
| Late fix | A valid late fix populates the origin only if the user has neither selected a place nor started typing (focus or input in the origin search field). A fix (in time or late) from any attempt, including one started by "Try location again", never replaces a manual origin: it is only offered. Only tapping "Use my current location" switches a manual origin back to GPS. With a manual origin set, "Try location again" is always available beside the origin (issue #13) and runs in the background: a spinner shows while it runs, and its denial, unanswered prompt, timeout, error or out-of-SG result changes no origin, only a note under it ("… Your chosen origin is kept."). "Change" can be cancelled with "Keep this origin". Each attempt has an id: a superseded attempt's fix, error or timeout is dropped and never counts as the current attempt's result | — | Guide §5.4. Reviewer rule on PR #3 |

| Conditions grid | Presentation only.
